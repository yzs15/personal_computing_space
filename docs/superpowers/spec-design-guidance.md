# Spec 设计原则（使用 superpowers 开发时必循）

**适用范围：** 本仓库内使用 superpowers 工作流（brainstorming → spec → plan → implementation）产出任何设计/spec 文档时，以下原则必须遵循。优先级高于 superpowers 默认 skill 行为；除非本文件另有说明，不修改 superpowers 自身的 skill 文档。

## 设计原则

1. **默认不考虑向后兼容** — 除非在 spec 中明确说明“本设计需要保持向后兼容”，否则接口、数据结构、行为均可按新目标直接重设计，不为旧调用方做兼容层。

2. **优先使用现成库与项目已有依赖** — 能由现成库或项目中已引入的依赖实现的，优先复用，不重复造轮子；引入新依赖前先确认无法复用现有能力。

3. **拒绝过度设计、过度抽象与过度防御式编程** — 只实现目标明确需要的抽象层与分支；不做用不上的泛化、不设多余的接口/基类/防护逻辑（YAGNI）。

4. **主动删除遗留过时代码** — 被新设计取代的旧实现、死代码、无用参数与废弃路径，在本次改动中一并删除，防止代码冗长。

5. **架构决策考虑长远演进** — 设计眼光放长，禁止临时的、只解决当下问题的方案；新设计应能平滑支撑后续合理演进（替换旧方案或引入新后端等）。

6. **减少防御性写法与无关反例** — spec 中的“范围外 / 反例 / 不做的事”只记录与本目标相关的内容，不罗列完全无关的非目标反例；不写过度防御性的措辞。
